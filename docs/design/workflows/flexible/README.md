## 1. What changes and why

The approved requirements add five ideas the current Workflow pages cannot show: **declared outcomes with "what happens next" rules**, **bounded repeat groups** (rounds, limit, escalation) plus a **run-level agent-turn allowance**, **feedback carried into each new round**, **reusable human approval policies** with gates that are separate from task acceptance, and **recovery that never repeats a public action**. The redesign in #350 keeps every control it had; this spec adds the surfaces for those five ideas and changes ten screens. Nothing here replaces prerequisites, the three-prerequisite rule, human-only Start and Finish, evidence or acceptance records.

Principles carried over from #350 plus four new ones:

1. **Explain in words first.** Every loop, branch and gate has a sentence ("Round 2 of 5 · exits when Review reports Passed · then asks Kedar"); the diagram is never the only explanation.
2. **Outcome ≠ permission.** A reviewer's "Passed" is shown as an outcome; a person's approval is shown as a decision with what it permits and which version it covers. They never share a control.
3. **Show the path not taken.** Unselected branches, stale work and overridden decisions stay visible with the rule or person that decided.
4. **Limits are visible before Start and at the limit.** The Start review lists routes, limits, approvers and anything incomplete; a reached limit or stall is an owner decision, never a silent round 6.

## 5. States, permissions, keyboard

- Loading, empty, forbidden, unreachable, stale and unsupported-server states follow #350 §5 unchanged. On a server without the capability, outcome, loop, gate and policy controls are hidden from Create and the Start review says "This server runs simple workflows"; existing runs render exactly as #350.
- Gate states: **waiting** (open, reminder and escalation dates shown); **partly approved** for an all-required policy ("Priya approved · waiting for Sam", the gate stays closed and nothing is permitted); **approved**; **changes requested**; **declined**; **expired** (the deadline passed and escalated; a reply after that is shown to the owner for review and is never applied by itself); **out of date** (the artifact changed after a decision, so the decision is kept in history and the gate reopens for the new version). Not drawn as frames; they reuse the x08 sheet with the state in the header.
- Editing a workflow while a run is active never changes that run: ordinary edits create a draft definition for later runs, and the running run keeps the definition it started with (the same rule x09 shows for policies). The Create page says so in its stepper line when a run is active.
- Only the step's assigned reviewer can report a review outcome; the producer's report form offers only its own outcomes. Only the workflow owner (or a human with the owner role) sees limit, stall, override and missing-outcome decisions. Agents never see approval controls.
- Everything is reachable by keyboard; status is never colour-only (badge text, round numbers and glyphs carry the meaning). Dialogs trap focus and return it to the opening control, as the primitives already do.

## 6. Decisions taken in this design

- Loops are drawn as a bracket around consecutive list rows, not as a back-edge in the graph; the Route tab shows return arrows separately from prerequisites.
- The Route tab replaces the Dependencies tab from #350 and keeps everything it had (prerequisite list and graph, prerequisite editing); nothing from #350 is removed, the tab is renamed because it now also shows outcome routes.
- "Request changes" is the name of the middle gate decision everywhere (PRD); "approve with edits" is its synonym and appears once, in the option's own description.
- Outcome reporting reuses the Result review dialog (#350 frame 05) with an outcome selector instead of a second "report" surface.
- Owner decisions at a limit, stall or missing outcome are sheets with options and consequences, not free-text chat.
- Gate approval is its own sheet, separate from task acceptance, with the version and the permitted action named.

## 7. API asks (for the architecture step)

What the current contract already has (`/openapi.json`, checked 2026-10-28): review loops as *pairs* (`ReviewHistory` with `loop_key`, `round_number`, `outcome`, `reviewed_artifact`, `resolved_by_owner`, `resolved_reason`; `WorkflowDetail.round_limit`, `limit_reached`, `review_rounds`; `POST /api/workflows/{wid}/review-rounds`; `POST /api/workflows/{wid}/review-loops/{tid}/resolve`), prerequisites, start/finish/completion checks, evidence and acceptance. It has no declared outcomes, routes, repeat groups beyond a review pair, per-round inputs, agent-turn allowances, stall records, approval policies, gate decisions or recovery receipts. The asks below **extend** the round model (round numbers, the round limit, `limit_reached` and the owner resolve stay) and **replace** the review-pair shape with a group of any member steps, as the requirements ask ("generalize beyond review pairs; separate logical steps, loop rounds and attempts"). In the order the walkthroughs use them:

1. **Step outcomes and routes** on the workflow definition: per step (and per gate), a list of outcome names and, per outcome, one destination (step, "ask owner", "exit group" or "end of route"); validation errors returned by the preview and start-check routes.
2. **Repeat groups** (replacing review pairs): name, member steps, review step, exit outcome, max rounds, escalation owner; run state with current round, rounds used, and per-round inputs (artifact versions, findings, reason). The **stall record** belongs here too: when two consecutive rounds report the same finding ids against an unchanged artifact version, the server pauses the group and returns the two rounds compared (finding ids, per-finding unchanged flag, artifact version per round) for x05.
3. **Outcome report** on a task: declared outcome, findings list, free text; only the assigned reporter may post it; the server returns the routing preview before commit, including held workers and whether a stop was confirmed.
4. **Owner decisions**: raise limit (new max, used count), reassign-and-continue, accept-with-override, stop; stall resume with a note, or accept-with-override at a stall; pick outcome for a missing one; resolve conflicting instructions. Each stored with the reason and the original outcome.
5. **Approval policies** (named, versioned) and **gate decisions** (approve, request changes, decline) bound to an artifact version, with the run-level eligibility (self-review exclusion) and the gate states in §5.
6. **Recovery records**: uncertain external actions with receipts, worker reconciliation state.
7. **Run-level agent-turn allowance**: a default on the definition (40), the value chosen at Start, turns used so far (x11 header), and an **allowance exhausted** owner decision (raise with the used count kept, reassign, change scope through owner review, stop); no new attempt starts while it is pending.

Nothing in this folder changes production code.
